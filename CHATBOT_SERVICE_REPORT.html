s3://<bucket>/document-chatbot/
├─ faiss/
│  ├─ index.faiss                 # 벡터 검색 인덱스
│  └─ index.pkl                   # 문서·메타데이터 매핑
├─ faq/
│  └─ faq.json                    # FAQ 내보내기·복구용 사본
├─ pdf/
│  └─ <logical_name>_v<N>.pdf     # 관리자가 올린 원본 PDF
└─ documents/
   └─ <logical_name>/
      └─ v<N>/
         ├─ document.md           # 검색에 사용할 변환 문서
         ├─ document.json         # 문서 처리 메타데이터
         ├─ chunks.json           # 검색 단위로 나눈 본문

embedding.json은 임베딩 작업 정보이며 실제 검색 벡터는 faiss/index.faiss에 들어갑니다. 문서 유형에 따라 document.json 대신 faq.json이 저장될 수 있습니다.

데이터가 이동하는 두 가지 핵심 흐름

사용자 질문과 답변

브라우저 → FastAPI로 질문 전송 → RDS에 세션·사용자 메시지 기록 → FAQ·최신 일정 또는 EC2의 FAISS 검색 → 필요 시 OpenAI 답변 생성 → 브라우저에 스트리밍 → 최종 답변·처리 방식·오류·비용을 RDS에 기록합니다.

관리자 문서 반영

PDF·Markdown 업로드 → 원본과 변환 산출물을 S3에 저장 → 문서 상태와 청크를 RDS에 기록 → 관리자 검토·승인 → 활성 문서와 FAQ 전체 재색인 → EC2에 FAISS 생성 → 동일 인덱스를 S3에 백업합니다.

복구 흐름: EC2에서 로컬 index.faiss가 없으면 서비스 시작 시 S3의 faiss/에서 인덱스를 내려받습니다. 따라서 RDS 백업뿐 아니라 S3 문서·FAISS 파일과 암호화 키의 복구 가능성도 함께 확인해야 합니다.

문서가 바뀌었을 때 서비스에 반영하는 법

01새 PDF·MD 버전 업로드
02Markdown 변환·청크 확인
03검토 후 승인 또는 반려
04승인 문서 자동 재인덱싱
05EC2 FAISS 저장·S3 동기화
06대표·회귀 질문 검증
07처리·감사 로그 확인
  1. 관리자 → 문서 검토에서 변경된 PDF 또는 Markdown을 새로 올립니다. 기존 파일을 서버에서 직접 덮어쓰지 않습니다.
  2. 같은 문서의 개정판은 파일의 기본 이름을 일관되게 유지해 새 version으로 쌓이게 합니다. 업로드 뒤 review 상태와 변환된 본문·청크 수를 확인합니다.
  3. 내용이 맞으면 승인합니다. 승인 시 같은 logical name의 이전 버전이 비활성화되고 새 문서가 ready / is_active=true가 되며 전체 인덱스가 자동 재구성됩니다.
  4. 잘못 변환됐으면 반려하고 원본을 고쳐 다시 업로드합니다. 복원된 문서는 즉시 활성화되지 않고 다시 검토·승인해야 합니다.
  5. 새 문서에서만 답할 수 있는 질문과 기존 핵심 질문을 함께 시험합니다. 새 답만 확인하면 기존 문서 검색이 깨진 사실을 놓칠 수 있습니다.

수동 “FAISS 인덱스 재구성”이 필요한 때: 승인했는데 검색에 반영되지 않을 때, EC2·S3의 index.faiss/index.pkl이 유실되거나 불일치할 때, DB·S3를 복구한 뒤, 또는 임베딩 모델을 변경했을 때입니다. 정상적인 문서 승인과 FAQ 저장·삭제는 현재 코드가 자동 재색인하므로 같은 작업을 반복할 필요는 없습니다.

인덱싱을 왜 하는가

청크 분할

긴 문서를 약 1,200자 단위와 150자 겹침으로 나눠 질문과 가까운 부분만 찾을 수 있게 합니다.

임베딩

각 청크의 의미를 숫자 벡터로 바꿉니다. 현재 text-embedding-3-large를 사용하며, 단어가 달라도 의미가 가까운 질문을 찾게 합니다.

FAISS 검색

질문 벡터와 가까운 문서 벡터를 빠르게 찾아 생성 모델에 근거로 전달합니다. PDF·RDS·S3에 파일만 저장한 상태로는 의미 기반 검색이 되지 않습니다.

비용과 주의점: 전체 재인덱싱은 활성 문서와 FAQ를 다시 읽고 OpenAI Embeddings API를 호출하므로 문서량만큼 시간과 비용이 듭니다. 임베딩 모델을 바꾸면 벡터 차원과 의미 공간이 달라질 수 있어 기존 FAISS 파일을 그대로 쓰지 말고 반드시 전체 재구성해야 합니다. OpenAI 공식 문서도 임베딩을 텍스트 간 관련성을 측정하는 수치 표현으로 설명합니다.

암호화·복호화는 어떻게 동작하는가

저장할 때

하나의 ENCRYPTION_KEY로 Fernet 대칭 암호화를 수행하고 저장값 앞에 enc::를 붙입니다. 채팅·문서 청크는 항상 보호하며 FAQ와 프롬프트는 설정의 카테고리별 ON/OFF에 따라 새 쓰기부터 적용됩니다.

읽을 때

API와 DB 브라우저가 enc::를 발견하면 같은 키로 복호화해 관리자에게 원문을 보여줍니다. 암호문과 키가 맞지 않으면 빈 값처럼 보일 수 있으므로 데이터 삭제로 판단하면 안 됩니다.

  1. 관리자 → 설정 → 암호화에서 FAQ·프롬프트·문서 카테고리의 암호화 건수와 평문 건수를 확인합니다.
  2. 토글은 이후 저장 방식을 바꿉니다. 기존 행까지 바꾸려면 별도의 전체 암호화 또는 전체 복호화 마이그레이션을 실행해야 합니다.
  3. 마이그레이션 전에 RDS snapshot을 만들고 ENCRYPTION_KEY 원본을 확인합니다. 복호화 실패 시 현재 코드는 원본 암호문을 빈 값으로 덮어쓰지 않도록 보호합니다.
  4. 운영 분석 때문에 복호화했다면 작업이 끝난 뒤 다시 암호화하고 건수를 대조합니다. 공개 보고서·Excel·로그에는 평문 개인정보를 남기지 않습니다.

현재 구현상 주의: 암호화 토글은 서버의 backend/.env에 기록되지만 배포 워크플로가 이 파일을 다시 만들며 기본값은 모두 ON입니다. 또한 문서 파일명·검토내용의 상태·마이그레이션 메뉴는 존재하지만 현재 업로드 코드는 문서 메타를 항상 maybe_encrypt()로 저장하므로 문서 OFF 토글과 새 쓰기 동작이 완전히 일치하지 않을 수 있습니다. 운영에서는 문서 암호화를 ON으로 간주하고, OFF가 필요하면 코드·배포 설정을 먼저 정비한 뒤 검증해야 합니다.

EC2AMI 공유/복사 또는 새 서버 구축 후 Python·Node·systemd·작업폴더와 self-hosted runner를 설치합니다.새 PEM/SSM 접속, chatbot.service, runner online, 디스크 경로·권한을 검증합니다. 기존 PEM은 새 계정 자원에 자동 승계되지 않습니다.
RDS이관 직전 manual snapshot을 만들고 새 계정에 공유·복사·복원하거나 승인된 DB migration을 수행합니다.암호화 snapshot 공유에는 KMS 공유·복사가 필요하며 AWS 관리형 키로 암호화된 snapshot은 그대로 공유할 수 없는 제한이 있습니다. 새 endpoint로 DATABASE_URL을 교체합니다.
S3새 bucket에 document-chatbot 전체 객체를 cross-account copy/sync하고 destination bucket 소유권·암호화·versioning을 설정합니다.객체 수·용량·checksum 또는 표본을 대조하고 새 계정이 객체 소유권을 갖는지 확인합니다. AWS_S3_BUCKET을 교체합니다.
비밀정보ENCRYPTION_KEY는 정확히 유지하고 새 RDS·S3·AWS 자격정보를 GitHub Secrets에 등록합니다.최소 변경 대상은 DATABASE_URL, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_S3_BUCKET입니다. IAM Role 적용 후에는 장기 AWS 키 제거를 검토합니다.
검색 인덱스S3의 기존 FAISS를 복사하되 새 환경에서 승인 문서 전체 재인덱싱을 1회 수행합니다.RDS 문서 상태, S3 원문과 EC2 인덱스가 같은 시점인지 확인하고 대표·회귀 질문을 실행합니다.
DNS·배포새 EC2 runner 배포가 성공한 뒤 DNS를 새 endpoint로 전환하고 TTL 동안 양쪽을 관찰합니다.기존 AWS 계정과 서버는 즉시 삭제하지 말고 합의한 안정화 기간 뒤 백업·로그를 확인하고 종료합니다.

PEM 키와 EC2 접속권한 이관

PEM은 무엇이며 왜 별도인가

PEM은 Linux EC2에 SSH로 접속할 때 사용하는 개인키입니다. 애플리케이션이 실행될 때 읽는 13개 값이 아니므로 GitHub Secrets에 넣지 않습니다. AWS는 private key 사본을 보관하지 않기 때문에 분실한 같은 PEM을 다시 내려받을 수 없습니다.

권장 인계 방식

기존 PEM 파일을 여러 사람이 공유하지 말고, 차기 담당자가 새 key pair를 만들게 합니다. 기존 담당자가 접속 가능한 동안 새 공개키를 서버의 ~/.ssh/authorized_keys에 추가하고 새 키 접속을 확인한 뒤, 최종 검증 후 기존 공개키를 제거합니다.

PEM 전환 순서: 새 key pair 생성 → private key를 차기 담당자의 승인된 금고에 저장 → 기존 접속으로 새 public key 추가 → ssh -i <new-key>.pem <user>@<host> 접속 시험 → 새 키로 sudo·서비스 로그·runner 상태 확인 → Session Manager 같은 비상 접속수단 확인 → D+7 이후 기존 public key 제거. 새 접속이 검증되기 전에는 기존 키를 먼저 제거하지 않습니다.
